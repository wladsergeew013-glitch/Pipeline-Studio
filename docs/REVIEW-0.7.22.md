# Pipeline Studio 0.7.22

Дата: 14 ноября 2026 года. База: `b9a2644dd4a8b9f774140491d1cb6bc56f8cb301` (0.7.21).

Кандидат [v0.7.22-rc.1](https://github.com/wladsergeew013-glitch/Pipeline-Studio/releases/tag/v0.7.22-rc.1), обновлённый после двух проходов ревью: исправлены V21-01…V21-23 и ограничен маршрут R21-01. Публикация предварительного выпуска требует успешного Linux и Windows CI точного коммита. Ссылки на выполненные CI, коммит и контрольные суммы файлов приводятся на странице выпуска. Проверки используют синтетические документы и отдельные тестовые профили. Предыдущая локальная поставка 0.7.22 сохранена отдельно в `review-fixes-20261114-r3/release-before-pass2`.

## R21-01 — нативный PDF viewer

До встраивания проверяются расширение/MIME и сигнатура `%PDF-x.y`. Desktop получает подписанный URL `studio-pdf://material/…`; обработчик повторно проверяет путь, подпись, права FileBridge и тип при каждом чтении. Он выдаёт только `application/pdf` с `nosniff`, без кэша, с поддержкой GET/HEAD, обычных и суффиксных Range и ответа 416.

Источник PDF имеет отдельный origin от файлового origin редактора. Его frame не получает native API, Node или доступ к DOM родителя. Проверяются HTML, HTML под расширением PDF, HTML в previewPath, подмена файла после stat и неподписанный URL. Проверяются реальный PDF plugin Chromium в Electron и изображение синтетической PDF-страницы.

Обычный iframe sandbox блокирует PDF plugin Electron. Для нативного PDF используется отдельный ограниченный протокол; произвольные HTML/сайты не выдаются через него. Ветка встраиваемого сайта сохраняет свой sandbox. Основания: [Electron protocol](https://www.electronjs.org/docs/latest/api/protocol), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security).

Это проверка маршрута просмотра. Эксплуатация уязвимостей самого PDF plugin и исчерпывающий аудит Electron не заявляются.

Docker-набор LibreOffice повторяет 26 серверных тестов и дополнительно закрывает единственный пропуск Windows; 26 повторных тестов не прибавляются к 86 как новые независимые случаи.

Исходный вывод об отсутствии LibreOffice был неполным: на машине есть образ `rag-assistant-libreoffice:ubuntu24.04` с Writer и Impress 24.2.7.2. Для запуска HTTP-тестов в отдельный временный производный образ добавлен Python; исходный worker и его данные не изменяются. Тест запускает настоящий сервер Pipeline Studio, загружает RTF/DOCX/PPTX, вызывает `/api/preview`, получает PDF через `/media` и сверяет неизменность оригиналов. Образ сервиса оформления документов также подтвердил RTF/DOCX, но не содержит Impress; итоговая проверка всех форматов использует образ LibreOffice worker.

Linux CI устанавливает Writer и Impress и выполняет тот же Office-тест в общем runner без пропуска. Windows CI использует `STUDIO_PORTABLE_STARTUP_TIMEOUT=120000`, как успешная локальная проверка. Журнал контейнерной проверки: `qa/office-docker-0722.log`; Dockerfile и журнал сборки тестового образа включены в evidence.

Граница portable-проверки: со штатным тайм-аутом 45 секунд второй запуск не успевал создать startup-отчёт; отдельно наблюдался такой же тайм-аут готового 0.7.21. С настройкой `STUDIO_PORTABLE_STARTUP_TIMEOUT=120000` текущая сборка прошла все три профиля, включая строчную букву диска, кириллицу, апостроф, `#` и `%`. Причина задержки не установлена. Это функциональная проверка запуска, открытия и сохранения, а не измерение производительности. Штатный порог теста остаётся 45 секунд.
